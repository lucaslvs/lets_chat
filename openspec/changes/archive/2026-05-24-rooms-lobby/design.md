## Context

The app currently has one Ash domain (`LetsChat.Accounts`) with magic-link authentication via AshAuthentication. There is no concept of a "room" yet — no domain, no resource, no routes, and no LiveViews beyond login. This change introduces the foundational `LetsChat.Chat` domain and its first resource, `Room`, along with a Lobby LiveView (`/rooms`) and a Room shell LiveView (`/rooms/:slug`). All real-time features (presence, messaging) are deferred to later changes; the goal here is to establish correct data structures and a complete UI skeleton so subsequent changes add logic without touching layout.

Tech stack: Phoenix 1.8.7 + LiveView 1.1.0, Ash 3.x + AshPostgres, DaisyUI + Tailwind (Kraken design system), Postgres.

## Goals / Non-Goals

**Goals:**
- Introduce `LetsChat.Chat` domain registered in `config/config.exs`
- Implement the `Room` resource with all attributes needed through Change 5 (`id`, `name`, `slug`, `visibility`, `owner_session_id`, `owner_user_id`, `inserted_at`)
- Auto-generate URL-safe slugs from room names with uniqueness collision handling
- Validate slug availability in real-time via `phx-change` on the creation form
- Implement `LobbyLive` (`/rooms`) with room list, empty state, and a modal for room creation
- Implement `RoomLive` (`/rooms/:slug`) as a complete HTML/CSS shell with disabled message input
- Route both LiveViews inside `ash_authentication_live_session` with an existing guest guard

**Non-Goals:**
- Real-time presence or online-count badges (Change 4)
- Private room access control or invite tokens (Change 5)
- Message persistence or delivery (Change 3)
- Room ownership enforcement or authorization policies beyond simple reads (later changes)
- Editing or deleting rooms

## Decisions

### 1. New `LetsChat.Chat` Ash domain

A separate domain isolates chat concerns from authentication. The pattern mirrors `LetsChat.Accounts`: a top-level module using `Ash.Domain` with `otp_app: :lets_chat`, registered in `config/config.exs` as `ash_domains: [LetsChat.Accounts, LetsChat.Chat]`.

**Alternatives considered:**
- Placing `Room` inside `LetsChat.Accounts` — rejected; conflates unrelated concerns and would require refactoring later.
- A single monolithic domain — rejected; contradicts Ash best-practice of domain-per-context.

### 2. `Room` attributes

| Attribute | Type | Constraint | Rationale |
|---|---|---|---|
| `id` | UUID | primary key | Standard Ash PK |
| `name` | string | required, non-empty | Display label shown in lobby cards |
| `slug` | string | required, unique, public_simple_equality | URL identifier; auto-derived from `name`, never editable post-create |
| `visibility` | atom enum `[:public, :private]` | default `:public` | Field added now to avoid a migration in Change 5; form restricts to `:public` in this change |
| `owner_session_id` | string | allow nil | Tracks guest ownership without requiring auth; nullable for Change 5 transition |
| `owner_user_id` | UUID | allow nil, references users | Nullable now; used for authenticated ownership in Change 5 |
| `inserted_at` | AshPostgres.Timestamptz | auto | Used for `inserted_at DESC` ordering in lobby |

`invite_token` is NOT included in this change — it is a Change 5 concern tied to private room access.

### 3. Slug generation strategy

Slugs are generated in a `before_action` hook on the `create` action:
1. Apply `Slug.slugify(name)` (the `slug` hex package).
2. Query the database for existing slugs that match `"#{base}-#{n}"` pattern.
3. Append a numeric suffix if needed (e.g., `elixir-study-group-2`).

This is done server-side in the action, not via a database trigger, keeping the logic in Elixir and testable. The LiveView also derives a preview slug client-side (via `phx-change`) to show the user before submit, but the authoritative slug is always generated by the server.

**Alternatives considered:**
- UUID-based slugs — rejected; not human-readable.
- Generating slug in a changeset validate step — rejected; uniqueness checks need DB access, so a `before_action` hook is the correct Ash primitive.

### 4. Slug availability check via `phx-change`

The creation modal uses `phx-change` with `debounce="300"` on the name input. The LiveView event handler:
1. Derives a candidate slug from the current name value (same `Slug.slugify/1` logic).
2. Calls a `check_slug_available/1` helper that runs a lightweight `Ash.count` or `exists?` query against `Room`.
3. Assigns `@slug_available` (boolean) to show `✓ available` or `✗ already taken` inline below the slug preview.

No slug uniqueness suffix is applied during validation — the suffix is only applied on actual creation. When the availability check returns "taken", the submit button is disabled, preventing the user from submitting a room with a conflicting name. The user must change the name to proceed. Note: a race condition remains possible (two users checking simultaneously), but the unique index on `rooms.slug` enforces integrity at the DB level as a final safeguard.

### 5. Lobby LiveView design

`LobbyLive` at `/rooms` is a single LiveView with two states managed by assigns:
- `@rooms` — list from `Room` `:list` action, ordered `inserted_at DESC`
- `@show_modal` — boolean driven by `?new=true` query param on mount and by button click
- `@form` — AshPhoenix form for room creation
- `@slug_preview` / `@slug_available` — derived on `phx-change`

The modal opens without page navigation (no live patch needed) via `@show_modal = true`. The deep-link pattern (`/rooms?new=true`) sets `@show_modal = true` during `handle_params`.

After successful creation, the LiveView redirects to `/rooms/:slug` via `push_navigate`.

### 6. Flash rendering and auto-dismiss in LobbyLive

The root layout (`root.html.heex`) renders only `@inner_content` with no flash output. To display flash messages in the lobby, `<.flash kind={:info} flash={@flash} />` and `<.flash kind={:error} flash={@flash} />` are placed at the top of `lobby_live.html.heex`.

Flash auto-dismisses after 5 seconds via `Process.send_after(self(), :clear_flash, 5_000)` scheduled in `mount/3` during the connected phase only (`connected?(socket)` guard). `handle_info(:clear_flash, socket)` calls `clear_flash(socket)`. Scheduling in `mount` (not `handle_params`) ensures a single timer per LiveView lifecycle regardless of in-LiveView navigation.

For the invalid-slug redirect, `push_navigate` (not `redirect`) is used with `put_flash` so the flash is embedded in the LiveView navigation payload and available in the connected phase of the target LiveView — plain `redirect` causes the flash to be consumed during the dead render and lost when the socket connects.

**Alternatives considered:**
- Auto-dismiss via CSS animation — rejected; cannot notify the server to clear `socket.assigns.flash`, causing the flash to reappear on re-renders.
- URL query param (`?flash_error=…`) — rejected; the flash would reappear on page refresh.

### 7. Room shell LiveView design

`RoomLive` at `/rooms/:slug` renders a complete layout — header with room name and "Leave" button, empty message area with placeholder text, participant sidebar placeholder, and a message input that is `disabled`. The disabled input is intentional: it documents that the feature exists but is not yet wired up, avoiding layout rework in Change 3.

The LiveView loads the `Room` via the `get_by_slug` action on mount. If the slug does not exist, it redirects to `/rooms` with a flash error.

### 8. Routing and auth guard

Both LiveViews are nested inside the existing `ash_authentication_live_session` scope in `router.ex`. The `require_guest_name` plug/hook from `LiveUserAuth` is reused to ensure a guest session exists before entering either LiveView; unauthenticated visitors are redirected to `/?return_to=<path>`.

**Alternatives considered:**
- A separate `live_session` block — rejected; duplicates session setup and differs from Change 1's established pattern.

## Risks / Trade-offs

- **Slug collision window** → A race between slug check and creation could result in a taken slug. The server-side suffix generator resolves this at creation time; the UI check is advisory only. Mitigation: unique index on `rooms.slug` enforces integrity at the DB level.

- **`visibility` field unused in UI** → The field is stored but the form hardcodes `:public`. A future developer could accidentally expose the field. Mitigation: document in the resource that the form gate is intentional and add a test asserting the create action defaults to `:public`.

- **`owner_session_id` / `owner_user_id` duality** → Two ownership columns exist from the start. The `owner_user_id` foreign key to users must allow nil and must not have a cascading delete until Change 5 defines the policy. Mitigation: migration sets `null: true, on_delete: :nothing` on the FK.

- **`slug` hex package dependency** → `Slug.slugify/1` must be added to `mix.exs`. It is a pure Elixir library with no native dependencies. Mitigation: verify version compatibility during implementation.

- **Disabled input UX** → Users may be confused by a visible but non-functional message input. Mitigation: add a tooltip or helper text ("Messaging coming soon") to clarify intent.

## Migration Plan

1. Add `{:slug, "~> 1.x"}` to `mix.exs` and run `mix deps.get`.
2. Add `LetsChat.Chat` to `ash_domains` in `config/config.exs`.
3. Create `lib/lets_chat/chat.ex` and `lib/lets_chat/chat/room.ex`.
4. Run `mix ash.codegen rooms_lobby` to generate the AshPostgres migration.
5. Run `mix ecto.migrate`.
6. Add routes to `router.ex` and create `LobbyLive` and `RoomLive` modules.
7. Verify with `mix test` and manual smoke test in dev.

Rollback: `mix ecto.rollback` reverts the migration; removing the domain from `ash_domains` and deleting the new files restores previous state with no data loss risk (table is new).

## Open Questions

- Should the lobby paginate rooms or load all? The current design loads all; pagination can be added in a later change if the list grows large.
- Should `owner_session_id` be stored as-is or hashed for privacy? Storing raw session ID leaks a session identifier in the DB. A SHA-256 hash would be safer but requires a helper on read. Deferred decision — Change 5 will define ownership semantics more precisely.
